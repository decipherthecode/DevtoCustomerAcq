How to Fill This Document

💡
Read this first — before you touch anything else. Every field has a 💡 instruction with a real example. Replace placeholder text [like this] with your actual information.

What is this document?

Your Integration Specification — a wiring diagram for your app. It describes every external service, API, database, and AI system you connect to. Without it, bugs are mysterious, teammates get confused, and handoffs break.

Who fills it?

Anyone building the product — developer, founder, freelancer, or non-technical PM. Every section is written in plain English with examples. Even a beginner can fill it.

When to fill it?

  • Start: Fill Sections 1–3 before writing a single line of code
  • Continue: Fill each Integration Card as you add each new service
  • Update: Every time an API key changes or a new endpoint is added
  • Review: Before each major milestone (Alpha → Beta → GA → 500 Customers)

  • Password policy enforced (min 8 chars, 1 uppercase, 1 number)

8 🔒

Security & Secrets Management

8.1 Secrets Management Rules

  • Use .env files locally — never commit them (.gitignore must include .env)
  • Use your platform's secret manager in production (e.g., Vercel Environment Variables, Railway Secrets, AWS Secrets Manager)
  • Rotate all API keys every 90 days minimum
  • Never log secrets — mask them in all log outputs
  • Use different keys for dev / staging / production

8.2 Key Rotation Schedule

SecretRotation FrequencyLast RotatedNext Rotation Due

JWT SecretEvery 90 days[YYYY-MM-DD][YYYY-MM-DD]
Database PasswordEvery 180 days[YYYY-MM-DD][YYYY-MM-DD]

8.3 Security Checklist

  • All external inputs validated and sanitized before use
  • SQL injection prevented (parameterized queries / ORM used)
  • XSS prevented (output escaping in frontend)
  • CORS configured to allow only trusted origins
  • HTTPS enforced on all environments
  • Webhook payloads signature-verified before processing
  • User-uploaded files virus-scanned before storage
  • Admin endpoints require additional authorization checks
  • Dependency vulnerabilities scanned (npm audit / Dependabot)
  • Error messages don't leak stack traces to users

9.3 Retry Strategy (Global Rules)

💡
Exponential backoff means waiting longer between each retry: 1s → 2s → 4s → give up. This avoids hammering a struggling service.
RuleValue

Initial Wait[e.g., 1 second]

Don't retry on400, 401, 403, 404, 422 — retrying won't fix these

Testing Checklist

  • Error cases tested (network failure, invalid credentials, rate limits)
  • Webhook signature verification tested
  • Retry logic tested (simulate 429 and 503 responses)
  • Circuit breaker behavior tested
  • Tests use mocks/sandboxes — no real money charged, no real emails sent
  • Integration tests run in CI/CD pipeline (GitHub Actions, etc.)

Launch Readiness Checklist

✅
Walk through each phase checklist before going live. Check off items as you complete them — they save in your browser.

🛠️ Phase 1: Development Complete

  • All Integration Cards filled for planned integrations
  • All credentials stored in .env — not hardcoded
  • .env added to .gitignore
  • All integrations working in local development environment
  • Unit tests passing for all integration modules
  • Error handling implemented for all integrations
  • Architecture diagram matches current implementation

🔬 Phase 2: Staging Ready

  • All integrations tested in staging environment
  • Staging uses separate credentials from production
  • Staging DB seeded with realistic (anonymized) test data
  • Webhook endpoints configured for staging
  • Cost monitoring set up — alerts configured
  • Integration tests running in CI/CD pipeline
  • HTTPS enforced on staging domain

🧪 Phase 3: Alpha Launch (First Real Users)
